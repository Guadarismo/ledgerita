## 1. Cambios implementados

### 1a. Validación de Nonce (anti-replay attacks)

**Archivo:** `ledgerita_core/src/state.rs`

- Nuevo campo `nonces: BTreeMap<Address, u64>` en `State` que trackea el último nonce usado por cada cuenta
- En `apply_transaction()`: se valida que `tx.nonce > current_nonce` (el nonce de la tx debe ser estrictamente mayor al último registrado)
- El nonce se actualiza después de cada transacción exitosa
- `generate_state_root()` ahora incluye los nonces en el hash (afecta el Merkle Root)
- 2 tests nuevos: `test_replay_attack_detected` y `test_old_nonce_rejected`

### 1b. Encriptación de Wallet

**Archivos:** `ledgerita_core/src/crypto.rs`, `ledgerita_core/src/main.rs`, `ledgerita_core/Cargo.toml`

- Nueva dependencia: `orion = "0.17"` (vendorizada en `local_deps/`)
- Cifrado usando **Argon2i** (derivación de clave) + **XChaCha20-Poly1305** (AEAD)
- Formato del archivo `~/.ledgerita/wallet.key`: `hex(salt_16bytes):hex(ciphertext_72bytes)` = 177 chars
- Password requerido vía variable de entorno `LEDGERITA_PASSWORD`
- `load_or_create_wallet(data_dir, password)` — acepta password, encripta al crear, desencripta al cargar
- `show_address(data_dir, password)` — igual, requiere password para mostrar dirección
- Migración automática: wallets legacy (hex plano) se re-encriptan al primer acceso con password
- 6 tests nuevos: roundtrip, wrong password, deterministic salt, wallet creación/recarga, legacy upgrade, wrong password load
- Mensaje de error claro cuando `LEDGERITA_PASSWORD` no está configurada

## 4. Pendientes para próxima sesión — Fase 2

### 4.1 Distribución de Fees (Economía)
- **Qué:** Los fees se descuentan del sender pero no se asignan a ningún validador (se queman)
- **Cómo hacerlo:**
  - Añadir concepto de "validador/reward address" en `apply_transaction()`
  - Acumular fees en un pool o asignarlos directamente al nodo que propaga la tx
  - Opción simple: añadir parámetro `validator: Address` a `apply_transaction()`, acreditarle el fee
  - Opción más elaborada: acumulador de fees en `State` que se distribuye en cada checkpoint
- **Archivos:** `state.rs`, quizá `transaction.rs`
- **Tests:** unitarios validando que el validador recibe el fee

### 4.2 Persistencia con Sled
- **Qué:** Reemplazar el `State` en memoria (BTreeMap) por una base de datos Sled persistente
- **Cómo hacerlo:**
  - Añadir `sled = "0.34"` (o versión estable) a `Cargo.toml`
  - Crear `src/storage.rs` con struct `Storage` que wrappea `sled::Db`
  - Tablas: `balances` (Address → u64), `nonces` (Address → u64)
  - `State` en memoria sigue existiendo para operaciones rápidas
  - `Storage::flush()` persiste el estado periódicamente y en shutdown
  - Cargar estado desde Sled al iniciar el nodo
- **Archivos:** `storage.rs` (nuevo), `state.rs`, `lib.rs`, `main.rs`, `Cargo.toml`
- **Tests:** crear state, persistir, reiniciar, verificar que los balances sobreviven
- **Nota:** Sled requiere feature `serde` o usar serialización manual con `bincode`/`rmp-serde`

### 4.3 Pruebas en servidores (Fase 2)
